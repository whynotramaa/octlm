<Label>Read the cells</Label>

## Save the past keys, compute only the new pair

[Day 2's GQA post](/blogs/gqa-and-kv-cache/) worked out the memory cost of these blue cells before any code stored them. [Day 4's sampling post](/blogs/sampling/) used the orange path, recompute everything every step. Day 5 finally builds the blue path, the one that reuses.

The first pass over a prompt computes a query, key and value for every position. And when you append one new token, the past tokens' keys and values don't change. So for $t$ generated positions after a one-token prompt, a simplified count of key and value projections is $1 + 2 + \cdots + t = t(t+1)/2$ without a cache, and just $t$ with one. But attention still reads all the past keys at each step, so the cache doesn't make decoding constant-time. GPU launches, memory traffic and the final vocabulary projection still cost time. The diagram shows saved work, not a measured speed ratio.

<Label>The implementation</Label>

## One pair of tensors per layer

`Decoder.forward_cached` takes a new chunk of tokens and an optional list of past `(key, value)` tensors. Each layer projects the new chunk, appends it to that layer's pair, runs attention against the full pair and returns the updated cache. `generate_cached` fills the cache from the prompt first, then sends one token per step. The original `forward` and `generate` are still there as the baseline to compare against.

<Source file="octlm/model.py" symbol="Decoder.forward_cached" />

RoPE rotates a key by its **absolute position** before the key gets stored. So on the next step the old keys have to keep their old angles, if you rotate the whole cache again the attention scores change. The cached call slices the position table starting from the number of tokens already cached, so a fresh query and key get the right offsets.

Then there's a masking trap which is less obvious. In a normal full pass the query and key lengths match and a triangular causal mask is enough. With a cache, a three-token update can have three queries and hundreds of keys. And PyTorch's `is_causal=True` on a non-square attention matrix uses upper-left alignment, which would make the new queries attend to the wrong prefix. So octlm builds an explicit mask from absolute row positions for multi-token updates. A one-token update doesn't need a mask at all, because every saved key is in its past.

<Source file="octlm/model.py" symbol="CausalSelfAttention.forward_cached" />

The cache is only for full SDPA attention, on purpose. A sliding-window or compressed-attention cache needs different eviction or pooling rules, so the function just rejects those configs. When generated text fills the trained 512-token context, `generate_cached` rebuilds the cache from the newest 512 tokens. That keeps the original generator's context behavior, but we lose the reuse at that boundary. The planned 64, 256 and 512-token measurements all stay inside the window anyway.

<Label>The memory tradeoff</Label>

## GQA is what makes this cache small enough

For one sequence the cache stores two tensors per layer, so its payload is

$$
2 \times L \times H_{kv} \times d_{head} \times T \times b
$$

where $L$ is layers, $H_{kv}$ is key-value heads, $d_{head}$ is the width per head, $T$ is cached positions and $b$ is bytes per element. The Day 4 model has 8 layers, 2 KV heads, 64 values per head and float16 values, so that's **4 KiB per cached position**, which means 256 KiB at 64, 1 MiB at 256 and 2 MiB at 512. That's tensor payload, before allocator overhead. With eight KV heads every one of these numbers would be four times bigger.

The benchmark adds up the *actual* key and value tensor sizes and asserts that they equal this formula. All three measured sizes passed.

<Label>Does it pay off ?</Label>

## Match the old tokens first, then time both paths

The matched control is Day 4's trained 26M modern checkpoint, temperature 0, batch size 1 and a BOS-only prompt. After warming up both paths, `octlm.day5 cache` times 64, 256 and 512 new tokens on the same device and dtype. It synchronizes CUDA around each timer and records naive and cached tokens per second, cache bytes and whether the greedy tokens are exactly equal. If even one token changes, the speed result doesn't count until parity is fixed.

<Source file="octlm/day5.py" symbol="stage_cache" />

The small-model CPU check matched all 12 generated tokens across an eight-token context boundary. A separate cached three-token call matched the full forward logits, which exercises the offset mask. And then the trained-checkpoint test matched **every greedy token** at all three lengths.

So the cached path was 10.6 to 15.8 percent faster in these single T4 timings. That's way smaller than the projection-count reduction would make you expect, because attention still reads every saved key, and the PyTorch calls and the vocabulary projection still take time. And one timing per length can't give us a stable speed distribution, so don't read too much into the exact numbers. Decision, keep the cached generator for full SDPA attention, and the generic generator stays for the other attention configs.
