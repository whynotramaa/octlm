A model reads integers, not text. So a tokenizer is basically the pair of functions that turns text into a list of integer IDs and back again. And its design decides a lot, how long every sequence is, what the model can even represent, and what one prediction actually means.

Day 1 built two tokenizers. This post is the first and simplest one, which is also on purpose the baseline for the second one.

<Label>Definition</Label>

## One character, one ID

The character tokenizer collects every distinct character in the training text, sorts them and numbers them. Four special tokens come first:

| ID | Token | Used for |
| ---: | --- | --- |
| 0 | `<\|pad\|>` | Filler at the end of a short block. Never a training target. |
| 1 | `<\|bos\|>` | Beginning of a document. |
| 2 | `<\|eos\|>` | End of a document. |
| 3 | `<\|unk\|>` | Any character the training text didn't have. |

Encoding looks each character up. Decoding looks each ID up and joins the characters. That's the whole algorithm, like literally:

`lookup.get(character, 3)` is the important bit. A character outside the vocabulary becomes ID 3, and there's no way back from that. Decoding ID 3 gives you `<|unk|>`, not the original character.

### So what happened ?

- English and Python encode cleanly, because `PLAN.md` is English prose with code-ish names in it. Every token is one character, so the token count equals the character count.
- The Japanese preset is almost all unknown. `PLAN.md` has no Japanese in it, so those characters just don't have an ID.
- The emoji are unknown for the same reason. One emoji is one character here, but it's four UTF-8 bytes.

## What we measured

Problem, we needed a tokenizer to compare BPE against, trained on the same text.

The character tokenizer learned 86 entries from `PLAN.md`, 4 specials and 82 characters. On the held-out file, `day-wise.md`, it produced 13,939 tokens for 13,939 bytes. That file is plain ASCII, so one character is one byte is one token.

On an unseen Unicode sample, 77.8 percent of the characters mapped to `<|unk|>`. That's bad.

<Label>The problems</Label>

## Why characters hurt, especially on code

Day 1's paper exercise asked for three reasons character tokens hurt a model that reads code. The note has these:

1. **Sequences get long.** Every character is a position. A 4-space indent is 4 positions, `return` is 6. Attention cost grows with the square of the length, and the context window fills up with syntax.
2. **The model spends its capacity spelling.** To predict `values` after `sum(`, a character model has to predict `v`, then `a`, then `l`, each one a separate decision. A tokenizer that has `values` as one token makes that one decision.
3. **Unknown characters destroy information.** The vocabulary is fixed at training time. A new symbol, an accented name or an emoji in a string literal becomes `<|unk|>`, and the model can't read or write it.

The small vocabulary does have one real advantage, every ID gets a lot of training data. The next tokenizer keeps that for its base alphabet and fixes all three problems.

<Label>The rules</Label>

## What every octlm tokenizer has to preserve

`AGENTS.md` sets rules that both tokenizers follow, and there are tests for each one:

- **Exact round trip.** Decoding the encoded text gives back the same string. No lowercasing and no Unicode normalization, so `é` written as one code point and `é` written as `e` plus a combining accent stay different.
- **Tabs, indentation and CRLF survive.** Code depends on whitespace.
- **Stable IDs.** Special-token IDs never move between versions, and loading a tokenizer file with different specials fails.
- **Ordinary text never becomes a special token.** If someone literally types `<|eos|>` into a document, it's encoded as characters, never as ID 2. Otherwise a document could end itself early, which is a pretty bad bug.

<Label>Skipped</Label>

## What we didn't build, and why

- **A bigger character vocabulary.** Training on more text would shrink the unknown rate, but no amount of training text covers every character in Unicode. Bytes do, and BPE is built on bytes.
- **Word-level tokens.** A word vocabulary has the unknown-token problem way worse than characters, and code is full of names no dictionary has.
