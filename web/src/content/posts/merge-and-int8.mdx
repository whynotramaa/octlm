The [fine-tuned adapters](/posts/sft-with-lora/) work, but they cost something at inference. Every adapted projection runs three matmuls instead of one: the base weight, then A, then B. This post folds the adapter into the base weights, checks the fold, and stores the result with [Day 5's int8 path](/posts/int8-weight-only/).

<Label>The merge</Label>

## One matmul instead of three

The adapter's contribution is linear in $x$, so it folds into the weight once:

$$
W_0 x + \frac{\alpha}{r} B A x = \Big(W_0 + \frac{\alpha}{r} B A\Big) x = W x
$$

After the merge, the model has the base model's shapes and speed. octlm computes $\frac{\alpha}{r} B A$ in float32, adds it to $W_0$ in float32, and casts the sum back to float16, as [PEFT](https://github.com/huggingface/peft/blob/main/src/peft/tuners/lora/layer.py) does.

<Label>A failed check</Label>

## The first gate was tighter than float16

The plan said to stop if merged and unmerged logits differed by more than 0.05, "the float16 rounding scale". The first T4 run measured {first.max_absolute_difference.toFixed(3)} on a {first.tokens}-token prompt and stopped before the int8 eval.

That looked like a broken merge. A float32 check on the laptop said otherwise:

In float32 the merge is exact to about $10^{-4}$. Rounding only the merged weights to float16 already costs {laptop[1]["Max logit difference"]}, and float16 activations across 28 blocks add the rest. The 0.05 was a guess. It was never measured, and it broke the project's own rule that a tolerance comes from a measured noise floor.

<Figure label="How big is one float16 step?" caption="float16 has 10 mantissa bits, so the gap between neighbouring values doubles with every power of two. Move the slider to see the step at any logit size.">
  <Float16Gap client:visible tolerance={0.05} measured={[{ name: "laptop f16 W", value: num(laptop[1]["Max logit difference"]) }, { name: "T4 run 1", value: first.max_absolute_difference }, { name: "T4 rerun", value: gate.max_absolute_difference }]} />
</Figure>

The largest logit on the prompt is about 38. Near 38, adjacent float16 values are $2^{5-10} = 0.031$ apart. Any tolerance near 0.05 sits within two rounding steps of the largest logits, so ordinary rounding trips it.

The new gate asks a question rounding can't fake. Do the merged and unmerged models pick the same top-1 token at every position of the prompt? It still logs the max difference. The float32 table is the proof that the math is right.

<Label>A confound</Label>

## The rerun trained a different adapter

The rerun's adapter hash is `{hash(env)}`. The first run's was `{hash(eval0[0])}`. Same code, same data, same seed, different bits. The two loss curves agree within 0.001 for the first ten steps, then drift apart. Step 42 is {step(train0, 42).toFixed(3)} in the first run and {step(rerun, 42).toFixed(3)} in the rerun.

<Figure label="Two seed-0 runs" caption="Seed 0 trained twice on a T4 with the same code and data. Nondeterministic GPU kernels and a few tokens of different tool output in the traces push the runs apart.">

Two things differ between the runs. Some CUDA kernels PyTorch uses in training are nondeterministic unless you ask for deterministic ones, and the [training traces](/posts/scripted-traces/) contain a random sandbox path and unittest timings that change from run to run. So the int8 eval below runs a different adapter from the float16 eval it's compared with.

The turn-limit stops doubled, from {fp.stops.turns} to {q.stops.turns}. Most of the rise is `answer` tasks, {stopsBy(a, "answer")} in float16 and {stopsBy(b, "answer")} in int8. The int8 model keeps reading files after it has the value, yet answers correctly as often. This eval can't say whether the new adapter or the int8 weights cause the looping, because both changed at once.

Speed went up, from {fp.generated_tokens_per_second.toFixed(1)} to {q.generated_tokens_per_second.toFixed(1)} tokens per second. The stock model ran at {base.generated_tokens_per_second.toFixed(1)}. Merging removes 14 adapter matmuls per block, and int8 dequantization costs less than they did. Day 5 found int8 slower than float16 on the 20M model, so the gain comes from the merge, not from int8. A float16 merged eval would measure the split. It wasn't run.

Decision: keep. The merge is exact in float32 and passes the top-1 gate. int8 halves the stored block weights, and pass^1 matches the float16 adapter. A fair comparison still needs the float16 eval of adapter `{hash(env)}`, one more 20-minute T4 run.

<Label>Skipped</Label>

## Not built

- **A float16 merged eval.** It would split the speed gain between the merge and int8, and remove the adapter confound. The exit check didn't need it.
- **int8 activations.** The weights are int8 but the matmuls run in float16 after dequantizing. True int8 matmuls need kernels PyTorch's eager mode doesn't offer on a T4.
- **Deterministic training.** `torch.use_deterministic_algorithms` would make the reruns match, at a speed cost. It would hide nothing the eval needs, so it can wait until a result depends on bit-exact reruns.
