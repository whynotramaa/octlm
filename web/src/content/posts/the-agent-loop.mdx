The transcript is just a list of messages. Following [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent), there's no hidden state and no persistent shell. Each turn appends to the list, and each tool call runs on its own. That keeps runs easy to replay, and Day 8 can use the transcripts as training data without converting them.

## Five tools, one directory

Every path goes through one function. It joins the path to the sandbox root, resolves `..` and symlinks, and refuses anything that lands outside the root. That covers both `../../etc/passwd` and an absolute path. Grep and list skip `__pycache__`.

`run_tests` starts `python -m unittest` in its own process session. Python's `subprocess` timeout only kills the direct child, so a test that starts a process of its own could outlive the {timeout}-second limit. On timeout, the harness kills the whole process group instead.

One more guard follows from Day 6. The rendered conversation gets encoded with Qwen's control tokens switched on, so a file that contained the literal text `<|im_end|>` would turn into a real end-of-turn token. Any tool result containing one of the tokenizer's added-token strings is replaced by an error.

This is path isolation, not a security boundary. `run_tests` executes Python the model wrote. That's why the eval runs on a throwaway Kaggle machine.

<Label>The cache</Label>

## Why appending tokens is wrong

Day 5 built a KV cache for one prompt. A tool loop has many prompts, and each one starts with the previous one. The obvious move is to keep the cache and append each new turn's tokens. Qwen's template makes that wrong.

In non-thinking mode, every generation prompt ends with an empty think block, `<think>\n\n</think>\n\n`. When the same assistant turn later appears in the history, the template renders it without that block. So the history the model would see by appending differs from the history the template produces, and the template is what the model was trained on.

So the harness re-renders the whole conversation every turn and compares token IDs:

$$
\text{keep} = \min\big(\text{LCP}(\text{cached}, \text{prompt}),\ |\text{prompt}| - 1\big)
$$

LCP is the length of the longest common prefix. The cache gets cut to `keep` positions, and only the rest is prefilled. The minus one ensures at least one token is prefilled, because the next token's logits come from the last prompt position. [Day 6's parity test](/blogs/logit-parity/) already showed that a cache built in two chunks matches a full forward pass, so a cut cache needs no new proof.

The hypothesis was that tasks of three or more turns would save more than half their prefill. They saved {pct(1 - fraction(long))}. One-turn runs save nothing, since their single prompt is all new. That's why the overall share is so high. The comparison needs no second run, because full prefill is just the sum of rendered prompt lengths, which the harness logs every turn.

The long-run row rests on {long.length} runs, because the stock model rarely takes a second turn. Day 8's fine-tuned model should produce many more.

Generation ran at {summary.generated_tokens_per_second.toFixed(1)} tokens per second on the T4. That includes each turn's prefill, so it sits below [Day 6's](/blogs/qwen-generation/) decode-only {decode.join(" and ")}.

Decision: keep prefix reuse.

<Label>Skipped</Label>

## Not built

- **Real isolation.** A container or a seccomp jail would contain model-written code. The throwaway VM does the job for now.
- **Parallel tool calls.** Calls in one turn run in order, which is what Qwen's guide describes.
- **A cache shared across tasks.** Every task starts with the same system prompt and schemas, so their cache could be computed once and copied. It would save {day7.system_tokens} prefill tokens per task, a small win next to generation time.
