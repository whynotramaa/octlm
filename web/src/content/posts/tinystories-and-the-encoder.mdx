Day 2's corpus held 2.96 million training tokens. The Day 4 model, 26 million parameters, needs about 400 million to get to a readable result. EXP-065 got the data, trained the tokenizer and encoded everything, and the first question was, can octlm's own Python encoder even do that in one session ?

<Label>The data</Label>

## TinyStories

TinyStories is a synthetic dataset of short children's stories, generated by GPT-3.5 and GPT-4 with a deliberately small vocabulary. Its authors report that models under about 30 million parameters trained on it write coherent, grammatical stories, which normally takes a way bigger model on web text. And that's exactly what the new plan needs from a 20M model.

octlm uses the V2 files, generated by GPT-4. The training file is 2,227,753,162 bytes and the validation file is 22.5 MB. The license is CDLA-Sharing-1.0.

A line with only `<|endoftext|>` on it separates stories, and sometimes blank lines follow it. The validation file starts in the middle of a story. The note's decision was to split on the delimiter line, strip surrounding newlines, drop empty stories, and keep the truncated first story, because dropping it would be a special case for one story out of thousands.

<Source file="octlm/day4.py" symbol="stories" />

Every story then gets encoded with `<|bos|>` and `<|eos|>` and appended to one flat file of 16-bit token IDs. Training reads random 513-token windows from that file through a memory map, so a window can span two stories with `<|eos|>` `<|bos|>` between them. The BPE merges still never cross a story boundary, because each story is encoded on its own.

## 8,192 entries from the first 10 million characters

The plan asked to choose between 4,096 and 8,192 entries by bits per byte. But bits per byte is a property of a trained model, so that choice would cost two full training runs. The TinyStories authors used a 10K vocabulary. So the note took 8,192, recorded the compression it gets, and moved the 4,096 comparison to Day 5 if GPU time allows.

[BPE training](/posts/byte-level-bpe/) recounts every pair after every merge, so its cost grows with the sample. The tokenizer trained on the first 10 million characters of the training split. TinyStories uses a small vocabulary, so a small sample covers it.

<Label>The encoder</Label>

## Every chunk always encodes the same way

Encoding a story means pre-tokenizing it into chunks, then running the merge loop on each chunk. And the merge loop only depends on the chunk's bytes. It never looks at the neighbors, because merges never cross a chunk boundary. So the same chunk always gives the same IDs, which means you can just store the answer after the first time.

### So what happened ?

- The first sentence is almost all misses, the cache is empty.
- By the third sentence most chunks are hits, `Lily`, `the`, `park`, spaces and periods.
- Paste a longer story and the hit rate climbs. TinyStories repeats a small vocabulary across 2.7 million stories, which is exactly the case this cache is built for.

The change is a dictionary on the tokenizer and three lines in `encode`. The output doesn't change, only the time.

## What we measured

Hypothesis, in two parts, the pure-Python encoder is too slow to encode 2.2 GB in one session, and the chunk cache fixes the merge cost while the per-character pre-tokenizer stays the bottleneck. Stop condition, if the training split takes more than two hours, stop and speed up the pre-tokenizer before training anything.

The benchmark encoded the first 2 million characters of the validation split twice, once calling the merge loop on every chunk, once through the cache starting empty. The Colab column is the note's EXP-065 table. The main run repeated the whole preparation on Kaggle two days later, and the Kaggle column is read from that run's `prepare.jsonl` and `bpe.jsonl`:

### So what happened ?

- The cache made encoding 6 times faster, from 427 KB/s to 2,559 KB/s.
- The training split, 966 million tokens, encoded in 934 seconds. That's 15.6 minutes against a two-hour limit, so the first half of the hypothesis was just wrong.
- The pre-tokenizer's cost wasn't measured on its own, so the second half stays open.
- Both splits compress to 2.262 bytes per token.
- 966 million tokens is 2.5 times what the main run uses, so the model sees each token at most once.
- Kaggle produced the same story counts, token counts and bytes per token. Only the times differ, Kaggle's CPU encoded the training split in {Math.round(split("train").seconds)} seconds, and the cache's speedup there was {(bench.cached_bytes_per_second / bench.plain_bytes_per_second).toFixed(1)}x.

Decision, keep the cache.

<Label>Skipped</Label>

## What we didn't build, and why

- **A Rust or C tokenizer.** The Python encoder met the stop condition with plenty of room.
- **Parallel encoding across processes.** Same reason.
- **The 4,096 vocabulary run.** Moved to Day 5, if GPU time allows.
- **Train-validation deduplication.** TinyStories ships separate files, and the note didn't check them for overlapping stories.
