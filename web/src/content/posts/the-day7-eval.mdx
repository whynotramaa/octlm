Day 8 will fine-tune Qwen to use tools. To know whether that worked, we need a fixed test that a script can grade, plus the stock model's score on it. This post builds that test and records the baseline.

Each `tests` task first plants one bug with an exact string replacement, such as `percent / 100` becoming `percent / 10`. The check also requires every original test file to be byte-identical, which blocks the obvious cheat of deleting or weakening the failing test. The `hidden` kind borrows SWE-bench's idea: grade new code with a test the model never sees.

<Label>Checking the checks</Label>

## Every task proves it can fail and pass

A check that always passes, or never can, quietly ruins an eval. SWE-bench runs every task's gold patch before using the task. octlm does the same with a `validate` stage that needs no model. Each task has a reference solution written as tool calls. For every task, `validate` confirms the check fails on the untouched repository. It then runs the reference calls through the real parser and tools, and confirms the check passes. For `answer` tasks it also confirms some tool output contains the answer, except two counting tasks whose answer no tool prints directly.

## Sampling makes one run a coin flip

The harness samples, as Qwen's model card recommends, so the same task can pass on one seed and fail on the next. Each task runs under seeds {seeds.join(", ")}, for {v2.length} runs in all. Two numbers summarize them. pass^1 is the plain success rate. pass^k comes from [tau-bench](https://arxiv.org/abs/2406.12045) and gives the chance that k independent tries all succeed. For a task with c successes in n tries:

$$
\text{pass}^k = \mathbb{E}_{\text{task}}\left[\frac{\binom{c}{k}}{\binom{n}{k}}\right]
\qquad
\text{pass@}k = 1 - \mathbb{E}_{\text{task}}\left[\frac{\binom{n-c}{k}}{\binom{n}{k}}\right]
$$

pass@k, the HumanEval metric, rewards a model that gets something right once. pass^k rewards one that's reliable. If a fine-tune only makes the model more consistent, pass^k moves first.

## Read the passing transcripts

Run 1 scored {Math.round(s1.pass_1_mean * v1.length)} passes. Reading those transcripts turned up two bad checks:

- `lamp-stock` passed with "{v1.find((r) => r.task === "lamp-stock" && r.seed === 2).answer}" The answer check tested for a substring, and "123" contains "12".
- `add-customer` passed twice after the model overwrote `data/customers.csv` with a header and the one new row, deleting the other seven customers. The file check only looked for the new line.

The plan written before the run said the task set freezes, and that any change means a new version and a new run, not an edit. So run 1 stays on record and v2 fixes both. An answer must now match as a whole token: no letter, digit, dot or dash just before it, and no letter, digit, dash or decimal part just after. File edits now also list original lines that have to survive. Run 2 scored the same tasks with the v2 checks. {flipped.length} runs changed from pass to fail.

That comparison is unusually clean. {same} of {v2.length} transcripts in run 2 match run 1 token for token. Fixed seeds reproduce sampled generation across two separate T4 sessions, so the scoring is the only thing that changed.

Even v2 has a known blind spot. {lucky.map((r) => `${r.task} on seed ${r.seed}`).join(", ")} passed without a single tool call. The model guessed a number and happened to be right. Only {grounded} of the {Math.round(s2.pass_1_mean * v2.length)} passes are grounded in a tool result. Every row stores its transcript, so Day 8 can report grounded success next to the raw rate without rerunning anything.

Decision: v2 is the Day 8 baseline. The fine-tuned model has to beat pass^1 {f3(s2.pass_1_mean)} by more than the seed spread of {f3(s2.pass_1_stdev)}, on the same tasks, seeds and limits.

<Label>Skipped</Label>

## Not built

- **An LLM judge.** Every check is a script. A judge could grade open-ended answers, but it brings its own biases, and this task set doesn't need one.
- **A bigger task set.** With {day7.tasks.length} tasks, one task is {f3(1 / day7.tasks.length)} of pass^1, as large as the seed spread. A stronger model would need more tasks to separate small gains.
- **Training traces.** Day 8 collects them from a separate fixture repository, so eval tasks can't leak into training.
