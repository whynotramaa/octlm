[LoRA](/posts/lora-from-scratch/) makes fine-tuning fit on a T4. Now we need something to fine-tune on: transcripts where a model reads the repository, calls tools in the right format, and finishes the task. This post builds {summary.tasks} of them.

<Label>Where traces come from</Label>

## Both planned sources fail

The plan offered two sources. Neither works here.

- **Filtered runs of the base model.** Run Qwen on training tasks and keep the runs that pass. The base model scores pass^1 {base.pass_1_mean.toFixed(3)} on the [Day 7 eval](/posts/the-day7-eval/). At that rate, {summary.tasks} training tasks would yield about two passing runs.
- **A stronger model through an API.** Anthropic's [Commercial Terms](https://www.anthropic.com/legal/commercial-terms), section D.4, forbid using the service "to build a competing product or service, including to train competing AI models". A larger open Qwen would work legally, but it needs another architecture check and GPU hours just to generate data.

So octlm takes a third route. Every training task already has a reference solution written as tool calls, because [task validation](/posts/the-day7-eval/) needs one. A scripted expert replays that solution through the real harness tools, in a fresh sandbox, and records what happened as a conversation. That's behavior cloning from a hand-written policy. It costs no GPU time and raises no license question.

<Label>Two rules</Label>

## The expert has to act like a model could

A replayed solution teaches whatever it contains, including shortcuts. Two rules make the traces teach the behavior Day 7 found missing.

1. **Read before you write.** Day 7's reference solutions write a file without reading it first. They were written to check the checks, and the author already knew the file. A model doesn't. Every training edit is preceded by a `read_file` of the same path. Bug fixes run the tests first, read the file, write the fix, and run the tests again.
2. **One call per turn, in the template's exact format.** Each assistant turn is `<tool_call>`, a newline, the JSON, a newline, and `</tool_call>`. The JSON comes from `json.dumps`, which escapes every newline inside a string. Raw newlines in `write_file` content were half of Day 7's invalid calls.

Each trace must pass its own task check before it is kept. A trace that fails stops the stage.

<Label>Keeping eval tasks out</Label>

## A different repository

If training tasks overlap the eval, the score measures memory, not skill. The eval runs on `shop`, a toy store package. Training uses `fixtures/day8/repo`, a different package called `library`, with its own config, data files, four modules and 14 tests. No training task shares a repository, file, function name, prompt or answer with an eval task, and the trace stage refuses to run if any training prompt equals an eval prompt.

The task kinds do repeat. Both sets have config lookups, file edits, new functions and planted bugs, because the point is to teach the tool protocol, not new skills. So the eval measures transfer to a new repository, not to new kinds of task.

<Label>From traces to examples</Label>

## One example per assistant turn

The obvious move is to render each conversation once and train on the whole thing. Qwen's chat template breaks that. It prints an empty `<think>\n\n</think>` block on the turn being generated, and drops it from every earlier assistant turn. A conversation rendered in one piece shows every turn but the last in a form the harness never produces at inference time.

So each assistant turn becomes its own example. The prompt is the conversation up to that turn, rendered with the generation prompt exactly as the harness renders it. The target is the reply plus `<|im_end|>`. The code encodes prompt and target as one string, then checks that the prompt's token IDs are a prefix of the result, so the boundary can never split a BPE merge.

The loss counts target tokens only. [QLoRA](https://arxiv.org/abs/2305.14314) found that training on targets alone beat training on prompt and target together on all four datasets it tried.

<Label>A correction</Label>

## The traces are not byte-for-byte reproducible

The plan claimed the trace file would be identical on every run. It isn't. The table above comes from the laptop. The Kaggle runs built the same traces with a different total, because three things in tool output vary:

- unittest prints `Ran 14 tests in 0.000s` on some runs and `0.001s` on others.
- Tracebacks name the sandbox, a random temporary directory that changes every run.
- The laptop's Python adds `~~~^^^` marker lines under traceback frames, and Kaggle's Python 3.12 mostly doesn't.

The targets don't change, because the loss mask skips tool results. All runs train on the same {int(summary.target_tokens)} target tokens. The context around them differs by a few tokens per run. Stripping the timing and the sandbox path would fix it, but that means editing the Day 7 harness, and the eval has to stay frozen.

<Label>Skipped</Label>

## Not built

- **Model-written traces.** A stronger open model could write more varied traces than a script. It costs GPU hours, and the scripted traces already passed the exit check.
- **Failed traces.** Some recipes train on recoveries from errors. Every octlm trace succeeds on the first try, so the model never sees a tool error being fixed.
- **More tasks.** {summary.tasks} tasks over four kinds is enough to teach a format. It isn't enough to teach debugging, and the results show it.
